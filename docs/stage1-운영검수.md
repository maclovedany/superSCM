## 0. 이 문서를 읽기 전에 — 무엇이 "확인됨"이고 무엇이 아닌가

이 저장소의 자동 검증은 전부 **로컬 임시 PostgreSQL**(`supabase/tests/*`)에서 돕니다. 배포용
Supabase 프로젝트에는 이번 stage1 SQL이 **아직 하나도 적용되지 않았습니다**
(`docs/stage1-supabase-수동적용.md` 참고). 그래서 아래 각 항목은 두 가지 상태 중 하나입니다.

- **로컬 DB로 증명됨** — `supabase/tests/<스위트>/scenarios.psql`의 시나리오 번호(S1, S2 …)를
  같이 적었습니다. 그 번호로 파일을 열면 정확히 무엇을 확인했는지 SQL로 볼 수 있습니다.
- **미확인 — 수동 실행 필요** — 로컬 DB 시나리오가 이 항목의 일부만 다루거나(예: 여러 화면을
  가로지르는 흐름 전체), Vercel/Supabase 운영 환경 설정에 의존하는 부분입니다. 실제 Supabase에
  SQL을 적용한 뒤 사용자가 화면에서 직접 눌러 봐야 합니다.

**로컬 DB 시나리오는 "SQL 함수가 규칙대로 동작한다"만 증명합니다.** 화면(Next.js)이 그 함수를
올바른 인자로 부르는지, 배포 환경의 Cron·이메일이 실제로 도는지는 이 문서의 "미확인" 항목이
사용자의 실제 클릭으로 확인해야 하는 부분입니다.

## 1. 전체 흐름 — 신규 수요 제출 → 승인 수요 → 재고 배정 → 발주계획 → 팀장 승인 → 일정 생성

| # | 확인할 것 | 기대 결과 | 상태 |
|---|---|---|---|
| 1-1 | 부서 담당자가 `/demand-submissions`에서 이번 달 수요를 입력하고 제출한다 | 제출본이 `SUBMITTED` 상태가 되고 SCM 품목담당자 화면에 보인다 | 로컬 DB로 증명됨 — `demand_submission` S3·S5 |
| 1-2 | SCM 품목담당자가 수급회의 결과를 입력해 합의 확정한다 | `core.supply_meeting_result`가 생기고 확정 수요에 반영된다 | 로컬 DB로 증명됨 — `approved_demand` S1·S11 |
| 1-3 | 영업담당자가 주문을 등록하고 검토를 요청한다 → 재고가 임시배정된다 | 가용재고에서 즉시 차감되고 두 영업담당자가 동시에 요청해도 초과 배정이 없다 | 로컬 DB로 증명됨 — `sales_order_allocation` S2 |
| 1-4 | SCM 품목담당자가 `/procurement-plans`에서 승인된 정책 값으로 발주계획을 계산·확정한다 | 목표 DoS·MOQ·Flex를 반영한 최종 발주량이 SQL에서 계산되어 나온다 | 로컬 DB로 증명됨 — `procurement_plan` S2·S3·S5·S6·S7 |
| 1-5 | SCM팀장이 `/approvals`에서 발주계획을 승인한다 | 승인 즉시 최종본이 되고 이후에는 불변이다 | 로컬 DB로 증명됨 — `procurement_plan` S14·S15 |

**미확인 — 수동 실행 필요.** 위 6단계를 로컬 DB 스위트는 **각자 다른 fixture로 따로** 검증합니다
(한 스위트가 6단계 전부를 연결해서 돌리지 않습니다). "1-1에서 만든 그 수요가 정말 1-4의 계획
계산에 들어가는가" 같은 **화면을 가로지르는 연결**은 실제 Supabase에 SQL을 적용하고 실제 계정
3~4개(영업담당자·SCM 품목담당자·SCM팀장)로 순서대로 눌러 봐야 확인됩니다. 오늘 배포 DB에는
재고 스냅샷 · 리드타임 · 목표 DoS · 공급처 매핑이 없으므로(§3 데이터 전제조건), 이 리허설은
지금 당장은 "null + 사유 코드"만 나오는 것이 정상입니다 — 값이 나오길 기대하지 마세요.

## 3. 데이터 전제조건 — 오늘 배포 DB로는 왜 숫자가 안 나오는가

오늘 배포 DB에는 재고 스냅샷, 리드타임, MOQ·단가, 등록된 공급처, 열린 취합 주기가 없고
사용 이력은 더미뿐입니다(memory: 실데이터에 재고·리드타임 없음). 그래서 이번 신규 화면은
**설계대로** null + 사유 코드만 보여줍니다. 이것은 버그가 아니라 "근거 없는 숫자를 만들지
않는다"는 이 프로젝트의 원칙입니다(AGENTS.md 5번). 아래를 받아야 실제 숫자가 나옵니다.

| 필요한 것 | 없으면 어떤 화면이 계속 null인가 |
|---|---|
| 공급처 마스터 + 품목→공급처 매핑 | 발주 일정(`SUPPLIER_UNSET`) |
| 법인별 출항 준비기간(prep_days) | 발주 일정(`PREP_DAYS_UNSET`) |
| 공급처별 출항일 규칙 | 발주 일정(`DEPARTURE_RULE_UNSET`) |
| 한국 공휴일 달력(대상월) | 발주 일정(`CALENDAR_NOT_READY`) |
| 재고 스냅샷(상태·창고 구분 포함) | 가용재고·배정·월말 재고 KPI |
| 승인된 품목 정책(목표 DoS·단가·MOQ) | 발주계획 확정 차단, 월말 재고금액 |
| 실제 사용 이력(더미 아닌 것) 재적재 | Forecast·Backtest 전부 `FORECAST_INPUT_UNTRACED`(§ 수동적용 문서) |
| 활성 취합 주기 열기(수요 제출 시작) | 부서 수요 제출·발주계획 계산 진입 자체 |

이 목록의 전체 근거와 우선순위는 (커밋되지 않는) `docs/데이터-요청목록.md`에 더 자세히 있습니다.
