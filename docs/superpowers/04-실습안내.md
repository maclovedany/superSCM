# 4회차 실습 안내

## 오늘의 목표

Supabase 의 실제 물류·사용 데이터를 분석해 공급처 리드타임 격차와 자재 사용 패턴을 읽고,
그 결과로 재고 소진 위험 계산 함수와 화면을 만듭니다.

## 시작 전 · 내 Supabase 에 DB 구축 (08:40–09:20)

**오늘부터 각자 자기 데이터베이스를 씁니다.** 강사 DB 를 같이 쓰면 12명이 서로 값을 덮어쓰고,
8회차에 각자 배포할 때 쓸 수 없습니다.

### 1. SQL 파일 여섯 개를 순서대로 실행

Supabase → SQL Editor → New query 에서 파일 하나씩 붙여넣고 Run 합니다.

```
01_schema  →  02_data_1  →  02_data_2  →  02_data_3  →  02_data_4  →  03_check
```

순서가 중요합니다. `01` 을 건너뛰면 `relation does not exist` 오류가 납니다.
꼬이면 `01` 부터 다시 실행하세요. 여러 번 실행해도 안전합니다.

### 2. 확인

`03_check.sql` 결과가 이렇게 나와야 합니다.

```
2864 · 7038 · 43 · 23 · 13 · 36 · 0 · 0 · 20
```

`core.leadtime_plan` 과 `core.usage_profile` 이 **0** 이어야 합니다. 오전 분석 결과로 채웁니다.

### 3. 스키마 노출

```
Project Settings → API → Data API → Exposed schemas
    public, core, analytics
```

이 설정을 빠뜨리면 **에러 없이 빈 배열**이 옵니다. 화면은 뜨는데 표만 비어 있습니다.

### 4. 앱 연결

```bash
git pull origin main
npm install
cp .env.local.example .env.local
npm run dev
```

`.env.local` 에 자기 프로젝트 값을 넣습니다.

| Supabase 화면                       | .env.local 변수                        |
| ----------------------------------- | -------------------------------------- |
| Project URL                         | `NEXT_PUBLIC_SUPABASE_URL`             |
| publishable 키 (`sb_publishable_…`) | `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` |

secret 키(`sb_secret_…`)는 쓰지 않습니다.

> Supabase 가 2025년에 키 체계를 바꿨습니다. 예전 `anon` 키가 publishable 키로 대체되었고,
> 최근에 만든 프로젝트에는 `anon` 이 아예 없습니다. `API Keys` 탭에서 찾으세요.

### 5. 화면 확인

| 주소                 | 기대                        |
| -------------------- | --------------------------- |
| `/`                  | 워크플로우 6단계            |
| `/analysis/leadtime` | **공급처 12행이 뜨면 성공** |
| `/analysis/stockout` | 404 — 오후에 만듭니다       |

## 준비 커밋에 무엇이 들어 있나

오후에 이 구조를 따라 새 기능을 만듭니다.

| 파일                                     | 역할          | 무엇을 하나                         |
| ---------------------------------------- | ------------- | ----------------------------------- |
| `lib/supabase.ts`                        | 연결          | URL 과 키로 Supabase 에 접속        |
| `lib/scm-model.ts`                       | 타입 · 정규화 | 받아온 값을 화면이 쓸 모양으로 정리 |
| `lib/scm.ts`                             | 조회          | analytics 뷰에서 데이터를 가져옴    |
| `components/analysis/analysis-frame.tsx` | 껍데기        | 제목 · 설명 틀                      |
| `components/analysis/data-table.tsx`     | 표            | 목록을 표로 그림                    |
| `app/analysis/leadtime/page.tsx`         | 조립          | 위 다섯을 합친 완성 화면            |

### 데이터가 흐르는 순서

```
page.tsx      화면 — 조립만 한다
    ↓ 부른다
scm.ts        조회 — analytics 뷰에서 가져온다
    ↓ 부른다
supabase.ts   연결 — URL 과 키로 접속한다

받아온 값은 scm-model.ts 를 거쳐 정리된 모양이 된다
```

아침에 배운 Raw · Core · Analytics 와 같은 사고방식입니다. 각 층이 자기 일만 합니다.

### scm-model.ts 를 따로 두는 이유

```ts
supplier: value(row, ['supplier_name', '법인', '공급업체명']) ?? '미정',
```

컬럼 이름 후보를 여러 개 적어뒀습니다.
Codex 로 뷰를 만들면 컬럼 이름이 달라질 수 있는데, 그래도 화면이 깨지지 않습니다.

**AI 가 만든 것을 방어하는 장치**입니다.
