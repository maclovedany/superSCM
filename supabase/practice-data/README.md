# 실습용(practice) 데이터

수업에서 **수요 제출 → 확정 수요 → 재고 배정 → 발주계획 → 팀장 승인 → 발주 일정**까지
전 구간을 실제로 눌러 볼 수 있도록 넣는 데이터입니다.

> ⚠️ **이것은 실적이 아닙니다.** 이 데이터로 계산된 발주량·재고금액은 수업용으로 지어낸
> 수요에서 나온 숫자입니다. 화면은 이 데이터가 깔려 있는 동안 **"이 화면의 숫자는 실습용
> 데이터 기반입니다"** 배너를 띄웁니다(`components/ui/practice-banner.tsx`).

## 왜 마이그레이션이 아니라 이 폴더인가

`supabase/migrations/*.sql`은 실제 운영 배포가 스키마를 맞출 때 전부 적용됩니다. 실습 데이터를
거기 넣으면 **운영 배포가 스키마를 적용하는 것만으로 더미 행이 함께 설치됩니다.** 그래서
표식·제거 장치(`20260912000400_stage1_practice_dataset.sql`)만 마이그레이션에 두고, 데이터
자체는 이 폴더에 분리했습니다. 이 폴더의 SQL은 **컨트롤러가 의도적으로 실행할 때만** 돕니다.

뒤 파일이 앞 파일이 만든 값(품목·학습 기간 등)을 전제합니다.

| 순서 | 파일 | 하는 일 |
|---|---|---|

| 0b | `00b-retire-legacy-usage.sql` | 5회차 더미(출처 없는) 사용 이력을 보관소로 옮김 — **되돌릴 수 있습니다**(아래 참고) |
| 0c | `00c-normalize-legacy-po-qty.sql` | 5회차 더미 발주수량의 콤마 텍스트('1,000')를 정규화(발주 화면 22P02 보정) — 실습 묶음 열림과 무관, **되돌릴 수 있습니다** |

| 3 | `03-item-policies.sql` | 품목 정책을 **승인 절차로** 설정(담당자 요청 → SCM팀장 승인). 목표 DoS·단가·MOQ |

### ⚠️ `09-build-plan.sql`은 되돌릴 수 없습니다

`core.procurement_plan`은 Task 9b의 트리거가 **DRAFT를 포함한 모든 상태에서 DELETE를 막습니다**
(승인본만이 아닙니다). 그래서 계획을 한 번 만들면 계획·라인·이력이 영구히 남고, 그 계획이
참조하는 Forecast 실행·Backtest·Champion과 계획 라인이 참조하는 품목·정책·적재 원본까지
함께 남습니다. 수업에서 발주계획 단계를 보여 줄 때만 실행하세요.

**실행 전 `08-verify.sql` 3절의 `source_status`가 `VERIFIED`인지 반드시 확인하세요.** VERIFIED가
아니면 모든 라인이 계산 불가인 계획이 영구히 남습니다(09가 스스로도 막습니다).

화면(`/procurement-plans`)에서 SCM 품목담당자 계정으로 "발주계획 계산"을 눌러도 결과는 같고,
같은 경고가 그대로 적용됩니다.

## ★ 이 데이터가 Forecast 원천 게이트를 통과하는 방식

Task 9b의 원천 게이트는 학습·검증 기간의 사용 이력이 **전부** `IMPORTED` 상태의
`usage_history` 적재 배치에서 왔고 `source_type='FILE_UPLOAD'`일 때만 발주량을 계산합니다
(`core.procurement_forecast_source_status`). 게이트를 **완화하지 않았습니다.** 대신:

1. 실습 사용 이력을 `core.upload_batch` → `core.import_staging` → `core.commit_import_batch`
   **진짜 적재 경로**로 넣습니다. 그래서 출처가 실제로 추적됩니다.
2. 배포 DB에는 5회차 더미 사용 이력 7,038행이 `batch_id = null`로 남아 있습니다. 학습 기간에
   그 행이 한 줄이라도 걸치면 게이트는 **정상적으로** 막습니다. `00b-retire-legacy-usage.sql`로
   그 행들을 보관소로 옮기면(되돌릴 수 있습니다) 제약이 사라져 학습 기간이 **실제 달력 월**에
   놓입니다 — 기준월 = 실행 시점의 **다음 달**.
   `00b`를 건너뛰면 `04-usage-history.sql`이 학습 기간을 **기존 미검증 행의 마지막 날짜 다음
   달부터** 잡습니다(하드코딩하지 않고 실행 시점에 계산합니다). 어느 쪽이든 선택된 기간은
   실행할 때 `notice`로 출력되고, 뒤로 밀린 경우 그 사실도 함께 알려 줍니다.

즉 **실습 데이터는 게이트를 우회하는 것이 아니라 게이트가 요구하는 조건을 진짜로 만족합니다.**
바꿔 말하면 이 숫자들은 "출처가 추적되는 데이터"일 뿐 "실제 업무 실적"은 아닙니다 — 그 구분을
화면 배너가 담당합니다.

## 5회차 더미 사용 이력 정리 (`00b`) — 되돌릴 수 있습니다

위 2번 때문에, 더미를 그대로 두면 실습 기간이 **실제 달력보다 미래**가 됩니다. `00b`는 출처 없는
행을 `core.retired_usage_history` **보관소로 옮깁니다.**

- **지우지 않습니다.** 원본 행을 jsonb로 그대로 보관합니다.
- **자동으로 되돌아옵니다.** `99-remove.sql`(= `core.remove_practice_dataset`)이 보관된 행을
  `raw.usage_history`로 되돌리고 보관소를 비웁니다.
- **출처가 있는 행은 한 줄도 건드리지 않습니다.** 판정 조건이 원천 게이트와 글자 그대로 같습니다.
- 보관 건수와 삭제 건수가 다르면 **정리 자체를 중단합니다**(복구 시 중복이 생기는 것을 막습니다).
- 현황은 `analytics.v_practice_retired_usage`와 `/admin/practice-data`에서 보입니다.

⚠️ 사용자가 만들지 않은 기존 데이터를 옮기므로 **실행 전에 백업을 받으세요.**

### ⚠️ 정리하면 5회차 화면 일부가 빕니다

`core.v_usage_effective`가 `raw.usage_history`를 **기간 제한 없이 전역 집계**하고, 그 값이
`analytics.v_stockout_risk`(재고 소진 위험)와 `analytics.v_usage_anomaly`(사용량 이상)로
들어갑니다. 그래서 **정리 시점부터 `99-remove.sql`로 되돌리기 전까지**:

| 화면 | 어떻게 보이는가 |
|---|---|
| `/analysis` 재고 소진 위험 | 5회차 더미 19품목의 `daily_usage_avg`가 null → `NO_USAGE`(계산 불가) |
| `/analysis` 사용량 이상 | 집계할 사용 이력이 없어 비어 보임 |
| `/dashboard` 관련 패널 · `v_data_coverage` | 데이터 기간이 함께 줄어듦 |

이 화면들은 5회차 더미 분석용이며 stage1 운영 흐름과는 무관합니다. 복구하면 그대로 돌아옵니다.
**그 화면을 수업에서 쓸 계획이면 이 정리를 하지 마세요**(대신 실습 기준월이 미래가 됩니다).

정리 후 기간은 이렇게 잡힙니다(실행 시점 기준).

| | 값 |
|---|---|
| 학습(train) | 이번 달 − 11개월 ~ 이번 달 − 3개월 |
| 검증(test) | 이번 달 − 2개월 ~ 이번 달 |
| **기준월(plan)** | **다음 달** |

이번 달이 아니라 다음 달로 잡는 이유는, 이번 달로 잡으면 제출 마감일(대상월 1일 − 2일)이 이미
지나 수업을 시작하자마자 미제출 반복 알림이 쌓이기 때문입니다.

## 품목코드를 지어내지 않습니다

품목코드는 `raw.dim_item`(실데이터 93,868행)에서 **조회해서** 씁니다. 하드코딩하지 않습니다.
지어낸 코드를 쓰면 나중에 실데이터와 조인이 깨지고, 실습 행과 실데이터 행을 구분할 수 없게
됩니다. `raw.dim_item` 자체는 **읽기만 하고 전혀 수정하지 않습니다.**

### 다만 품목구분(용지 · 카드리더기 · 소모품)은 실습용으로 **부여한** 값입니다

`dim_item`의 실제 분류가 stage1의 부서별 조회 범위(`core.item_visibility_rule`)와 매핑되지 않아,
마케팅부·서비스부 화면에도 무언가 보이도록 순번으로 나눠 넣습니다. 실제 품목 속성이 아니며
등기부 `note`에 그대로 적혀 `/admin/practice-data` 화면에 드러납니다
(`seq:N · 품목구분 …(실습용으로 부여, dim_item의 실제 분류 아님)`).

## 공휴일은 2026년만 넣습니다

`01-master.sql`은 **실제로 넣은 2026년 공휴일이 있는 달만** 준비됨으로 표시합니다. 공휴일을
넣지 않은 해를 준비됨으로 표시하면 영업일 보정이 주말만 보고 **공휴일을 평일로 취급**하는데,
그것은 "공휴일 자료가 없는 국가는 추정하지 않는다"(Task 10b)를 정면으로 어깁니다.

`00b`를 실행하면 기준월이 **다음 달**이라 발주일·입고일이 모두 2026년 안에 들어오고, 이
달력만으로 충분합니다.

⚠️ `00b`를 건너뛰어 실습 기간이 2026년을 벗어나면 발주 일정이 `CALENDAR_NOT_READY`로 나옵니다.
그 해 공휴일을 `/admin/master`에서 넣고 해당 달을 준비됨으로 표시하세요 — 추정해서 채우는 것보다
낫습니다. `04`가 기간이 밀렸다는 사실을 `notice`로 알려 줍니다.

## 제거

`99-remove.sql`에 확인 쿼리까지 함께 있습니다. 무엇이 지워졌고(`removed`) 무엇이 왜 남았는지

### 지워지는 것

등기부(`core.practice_object`)에 올라 있는 것만 지웁니다. **실데이터는 등기부에 없으므로
구조적으로 지워질 수 없습니다.** 적재 원본은 `batch_id`로만 지우므로 `batch_id`가 null인
5회차 더미·실데이터 행은 어떤 경우에도 걸리지 않습니다.

### 지워지지 않는 것 (그리고 왜)

| 남는 것 | 사유 코드 | 이유 |
|---|---|---|
| 발주계획 · 라인 · 이력 | `PLAN_IMMUTABLE_HISTORY` | Task 9b 트리거가 **DRAFT를 포함한 모든 상태에서** DELETE를 금지합니다 |
| 그 계획이 쓴 Forecast 실행 · Backtest · Champion | `PLAN_IMMUTABLE_HISTORY` | 계획이 `on delete restrict`로 참조합니다 |

### 되돌리는 것

`00-open-dataset.sql`이 실행 전 상태를 `core.practice_dataset.restore_payload`에 기록합니다.
제거할 때 법인 출항 준비기간(`prep_days`)과 기존 활성 Forecast 설정이 원래 값으로 돌아갑니다.
