# 실습용(practice) 데이터

수업에서 **수요 제출 → 확정 수요 → 재고 배정 → 발주계획 → 팀장 승인 → 발주 일정**까지
전 구간을 실제로 눌러 볼 수 있도록 넣는 데이터입니다.

> ⚠️ **이것은 실적이 아닙니다.** 이 데이터로 계산된 발주량·재고금액은 수업용으로 지어낸
> 수요에서 나온 숫자입니다. 화면은 이 데이터가 깔려 있는 동안 **"이 화면의 숫자는 실습용
> 데이터 기반입니다"** 배너를 띄웁니다(`components/ui/practice-banner.tsx`).

## 왜 마이그레이션이 아니라 이 폴더인가

`supabase/migrations/*.sql`은 실제 운영 배포가 스키마를 맞출 때 전부 적용됩니다. 실습 데이터를
거기 넣으면 **운영 배포가 스키마를 적용하는 것만으로 더미 행이 함께 설치됩니다.** 그래서
표식·제거 장치(`20260912000400_stage1_practice_dataset.sql`)만 마이그레이션에 두고, 데이터
자체는 이 폴더에 분리했습니다. 이 폴더의 SQL은 **컨트롤러가 의도적으로 실행할 때만** 돕니다.

## 실행 순서

Supabase SQL Editor에서 파일 하나를 통째로 붙여넣고 Run, 다음 번호로. **순서를 지키세요** —
뒤 파일이 앞 파일이 만든 값(품목·학습 기간 등)을 전제합니다.

| 순서 | 파일 | 하는 일 |
|---|---|---|
| 0 | `00-open-dataset.sql` | 실습 묶음 `PRACTICE-2026-09`를 열고, 되돌릴 값(법인 준비기간·기존 Forecast 설정)을 먼저 기록 |
| 1 | `01-master.sql` | 법인 출항 준비기간 · 공급처 5곳 · 출항일 규칙 · 2026 한국 공휴일 · 달력 준비 표시 |
| 2 | `02-items.sql` | `raw.dim_item`(실데이터)에서 **진짜 품목코드 11개를 골라** STEP 4 적재 경로로 품목 마스터에 넣음 |
| 3 | `03-item-policies.sql` | 품목 정책을 **승인 절차로** 설정(담당자 요청 → SCM팀장 승인). 목표 DoS·단가·MOQ |
| 4 | `04-usage-history.sql` | 12개월 사용 이력을 STEP 4 적재 경로로 넣고 학습/검증 기간을 정함 |

| 7 | `07-planning-cycle.sql` | 기준월 취합 주기 열기 |
| 8 | `08-verify.sql` | ★ **여기서 확인하고 넘어갑니다** — 원천 게이트 통과 여부, 화면별 기대값 |
| — | `99-remove.sql` | 제거(문서화된 한 번의 명령) |

### 먼저 필요한 것

- `supabase/migrations/20260912000400_stage1_practice_dataset.sql`이 적용되어 있어야 합니다.
- `docs/stage1-supabase-수동적용.md` §9의 실습 계정 6개가 있어야 합니다. 스크립트가 이메일로
  찾아 그 사람 자격으로 요청·승인합니다(요청자 ≠ 승인자 규칙을 우회하지 않습니다).

## ★ 이 데이터가 Forecast 원천 게이트를 통과하는 방식

Task 9b의 원천 게이트는 학습·검증 기간의 사용 이력이 **전부** `IMPORTED` 상태의
`usage_history` 적재 배치에서 왔고 `source_type='FILE_UPLOAD'`일 때만 발주량을 계산합니다
(`core.procurement_forecast_source_status`). 게이트를 **완화하지 않았습니다.** 대신:

1. 실습 사용 이력을 `core.upload_batch` → `core.import_staging` → `core.commit_import_batch`
   **진짜 적재 경로**로 넣습니다. 그래서 출처가 실제로 추적됩니다.
2. 배포 DB에는 5회차 더미 사용 이력 7,038행이 `batch_id = null`로 남아 있습니다. 학습 기간에
   그 행이 한 줄이라도 걸치면 게이트는 **정상적으로** 막습니다. 그래서 `04-usage-history.sql`은
   학습 기간을 **기존 미검증 행의 마지막 날짜 다음 달부터** 잡습니다(하드코딩하지 않고 실행
   시점에 계산합니다). 선택된 기간은 실행할 때 `notice`로 출력됩니다.

즉 **실습 데이터는 게이트를 우회하는 것이 아니라 게이트가 요구하는 조건을 진짜로 만족합니다.**
바꿔 말하면 이 숫자들은 "출처가 추적되는 데이터"일 뿐 "실제 업무 실적"은 아닙니다 — 그 구분을
화면 배너가 담당합니다.

## 품목코드를 지어내지 않습니다

품목코드는 `raw.dim_item`(실데이터 93,868행)에서 **조회해서** 씁니다. 하드코딩하지 않습니다.
지어낸 코드를 쓰면 나중에 실데이터와 조인이 깨지고, 실습 행과 실데이터 행을 구분할 수 없게
됩니다. `raw.dim_item` 자체는 **읽기만 하고 전혀 수정하지 않습니다.**

## 제거

```sql
select jsonb_pretty(core.remove_practice_dataset('PRACTICE-2026-09', p_confirm => true));
```

`99-remove.sql`에 확인 쿼리까지 함께 있습니다. 무엇이 지워졌고(`removed`) 무엇이 왜 남았는지
(`blocked`)를 JSON으로 돌려줍니다.

### 지워지는 것

등기부(`core.practice_object`)에 올라 있는 것만 지웁니다. **실데이터는 등기부에 없으므로
구조적으로 지워질 수 없습니다.** 적재 원본은 `batch_id`로만 지우므로 `batch_id`가 null인
5회차 더미·실데이터 행은 어떤 경우에도 걸리지 않습니다.

### 지워지지 않는 것 (그리고 왜)

| 남는 것 | 이유 |
|---|---|
| 승인된 발주계획 · 라인 · 이력 | Task 9b가 트리거로 **삭제를 금지**합니다(승인 기록은 불변) |
| 그 계획이 쓴 Forecast 실행 | 계획이 `on delete restrict`로 참조합니다 |
| 학생이 실습 품목으로 만든 주문·배정·긴급발주·수급회의·이벤트 수요 | 사람이 실제로 한 업무이고 승인·알림 이력이 매달려 있습니다 |
| 실제 입고일이 입력된 발주 일정의 공급처 | 사람이 입력한 값입니다 |
| `core.audit_log` · 승인 요청 · 알림 발송 이력 | append-only 감사 기록입니다 |

**남은 객체의 등기는 일부러 지우지 않습니다.** 그래야 살아남은 실습 발주계획이 화면에서
계속 "실습용"으로 표시됩니다 — 제거했다는 이유로 실습 숫자가 실적처럼 보이면 안 됩니다.

### 되돌리는 것

`00-open-dataset.sql`이 실행 전 상태를 `core.practice_dataset.restore_payload`에 기록합니다.
제거할 때 법인 출항 준비기간(`prep_days`)과 기존 활성 Forecast 설정이 원래 값으로 돌아갑니다.

## 수업 중에 값을 바꾸려면

전부 관리자·업무 화면에서 바꿀 수 있습니다. SQL을 다시 돌릴 필요가 없습니다.

| seed한 것 | 바꾸는 화면 |
|---|---|
| 법인 출항 준비기간 · 공급처 · 출항일 규칙 · 공휴일 | `/admin/master` |
| 품목 정책(목표 DoS · 단가 · MOQ) | `/procurement-plans/item-policies` (요청) → `/approvals` (승인) |
| 재고 · 사용 이력 · 품목 마스터 | `/admin/data-management` (같은 종류로 재업로드) |
| 취합 주기 | `/demand-submissions` |
| 발주계획 재계산 | `/procurement-plans` |
| 실습 묶음 현황 확인 | `/admin/practice-data` |
